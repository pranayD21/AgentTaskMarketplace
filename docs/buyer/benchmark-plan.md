# B1 benchmark protocol: atm-bounded-v1

Protocol fixed before inference runs on 2026-10-18. This is a small, reproducible check of bounded structured tasks. It is not a general intelligence benchmark, a production load test, or evidence of savings. Report missing arms and resource costs explicitly.

## Workload and quality criterion

The first-party synthetic dataset is generated by [workloads.mjs](../../scripts/benchmarks/workloads.mjs), dedicated to the public domain under [CC0-1.0](https://creativecommons.org/publicdomain/zero/1.0/). These are intentionally public fixture definitions, not customer task data. The generator contains the exact prompt templates, deterministic inputs, expected structures, worker system instruction and case SHA-256 computation. Six cases, all selected:

| Case IDs | Versioned inputs | Required result |
| --- | --- | --- |
| invoice-1, invoice-2 | Seeds 17 and 29; three units at seed × 11 cents and two at seed × 7 cents | A JSON object with exactly one integer total_cents field equal to the computed total. |
| sort-1, sort-2 | Integer lists [37,12,37,5,21] and [14,8,31,8,3] | A JSON object with exactly one values array, deduplicated and sorted ascending. |
| inventory-1, inventory-2 | Seeds 4 and 7; repeated-color quantities specified in the generator | A JSON object with exactly blue, green and red integer totals. |

Each arm uses the same six cases twice: **12 measured requests per arm**, concurrency one. The seeded Fisher–Yates ordering uses seed 20261018 and is the same for every arm. The plan-only command prints the order and configuration fingerprint. JSON parsing and recursive canonical equality reject extra prose, extra keys, wrong numbers and wrong ordering. No LLM grader is used for benchmark quality.

The marketplace's separate `contains_text` rubric checks the required output key. It controls marketplace review but is weaker than benchmark quality; an approved marketplace task can still fail the benchmark. Count only original seller results with `commitment_verified=true` and APPROVED status. A judge replacement is not silently counted as an original-model success.

## Three paired arms

1. **Direct local:** Ollama qwen3:8b, exact installed digest recorded at run time. Use the same physical seller hardware and model digest as the marketplace arm. The published tag currently identifies Q4_K_M / 8.19B parameters and an Apache-2.0 license; the tag alone is not a version pin. [Ollama model page](https://ollama.com/library/qwen3:8b).
2. **Marketplace:** hosted MCP, existing authorized buyer, qwen3:8b, posted offer 100 Stripe TEST cents per case, max runtime 180 seconds, expires after 600 seconds, bounded 240-second buyer wait. Record task/seller IDs, review and payment states, commitment flag, runtime and synthetic test charges. Join C/E/A measurements by IDs when their shared usage contract is published.
3. **Closed-source baseline:** Anthropic **claude-haiku-4-5-20251001**, a pinned legacy model, with availability checked through the Models API before each run. It is one named baseline, not a claim about the cheapest or strongest current closed-source alternative. Its published context limit is 200K tokens. [Official model specification](https://platform.claude.com/docs/en/models/haiku-4-5/overview).

All arms receive the identical generated instruction and worker system text. Settings match the current seller runner: temperature 0.2, at most 256 output tokens, no extended thinking, one request at a time, no automatic retry. Local requests use `think:false`; Anthropic omits extended thinking. Server/tool polling contributes to marketplace end-to-end latency. Versions and settings must be reported rather than assumed equivalent beyond these controls.

## Cold, warm and timing

Direct-local warm runs issue one model-load request before measured samples and record its timing separately. Each measured call records Ollama load, prompt-evaluation and inference durations, plus wall latency. Warm is a requested condition; inspect load duration for eviction or interference. Cold runs unload before each sample **only on a dedicated Ollama instance** with `--dedicated-ollama`; never unload C/D's shared live workers. If no dedicated instance is available, cold evidence remains unrun. [Ollama chat API fields](https://docs.ollama.com/api/chat).

Report quality success / all attempted cases, failure rate, completed-request p50/p95 using nearest rank, completed requests per wall-clock second, retries, and timeouts separately. Latency quantiles include completed quality failures and exclude non-completing timeouts, which remain visible in failure counts. Twelve samples make p95 essentially the observed maximum; do not present it as a stable tail estimate. Arms run in different sessions/machines, so record timing and avoid attributing every difference to model performance. No automatic retry or silent removal of failed cases is allowed.

## Budget and cost accounting

The human authorized **$5 total external API spend**, shared across this benchmark's baseline/controller/judge/replacement calls, not per arm, machine or run. B coordinates the durable ledger with D. No new controller LLM is used by this deterministic harness. Stripe TEST cents are separate from that API budget and are not measured inference costs.

The baseline uses standard synchronous Claude API rates, checked 2026-10-18: Haiku 4.5 input $1/M tokens, output $5/M, cache reads $0.10/M; cache writes are conservatively priced at the $2/M one-hour rate if returned. This harness requests no caching. Provider counts are recorded explicitly; absent counts remain unknown. These are rate-based usage estimates, not an invoice. [Official pricing](https://platform.claude.com/docs/en/about-claude/pricing).

Before a baseline request, the persistent `.atm-state/benchmark-api-budget.json` ledger reserves the model's full 200K context at the highest relevant cache-write rate plus 256 output tokens ($0.40128). After a complete response, it books the reported token cost and releases the unused reservation. Missing usage or uncertain transport outcomes retain the reservation. Reservations are atomic, fsynced and protected by an exclusive lock. A crash never grants a new allowance. Do not delete the ledger or clear a stale lock without reconciling its owner and in-flight requests.

Marketplace execution additionally requires a D-reviewed worst-case judge/replacement API reservation per case and an explicit existing-buyer test budget. A deterministic `contains_text` approval uses no provider grading/replacement call; unsuccessful or uncertain paths retain the API reservation until E/D supply usage. The initial 12-case plan needs up to 1,200 test cents of existing authorized capacity. Never raise the 25-cent Armature buyer's cap or create a substitute identity to run it. C/D/A must confirm the benchmark and physical rehearsal allocation on an existing authorized buyer before the marketplace arm runs.

D publishes two ledgers: buyer cost (marketplace price and controller/baseline API costs) and system resource cost (local energy, stated hardware amortization, hosting/database/MCP calls, judge/replacement attempts and relevant fees). Do not count a seller transfer twice. Failed-attempt costs stay in the numerator; divide by quality successes only when success count is nonzero. Unknown energy, hardware, hosting or API usage is null, never zero. Report the fraction of cost components known. No complete cost-per-success or savings claim is allowed until all three quality-matched arms and those components exist.

## Reproducible commands

```sh
# Offline checks and redacted plan; no paid calls.
node --test scripts/benchmarks/benchmark.test.mjs
node scripts/benchmarks/run.mjs --arm baseline --run-id bounded-v1

# B: authorized baseline. A repeated command resumes without repeating completed samples.
node scripts/benchmarks/run.mjs --arm baseline --run-id bounded-v1 --execute

# C: same workload on the real seller's local Ollama, with installed digest recorded.
OLLAMA_URL=http://localhost:11434 node scripts/benchmarks/run.mjs --arm local --computer C --run-id bounded-v1 --execute

# Dedicated instance only; do not use on the shared live seller.
OLLAMA_URL=http://localhost:11435 node scripts/benchmarks/run.mjs --arm local --computer C --phase cold --dedicated-ollama --run-id bounded-v1 --execute

# After A/D confirm the existing buyer allocation and D supplies a worst-case API amount:
node scripts/benchmarks/run.mjs --arm marketplace --run-id bounded-v1 --marketplace-budget-cents 1200 --judge-reservation-usd "$D_REVIEWED_RESERVATION_USD" --execute
```

Credentials are read from private environment/local buyer state and never included in commands, results or artifacts. The marketplace arm never registers a buyer. An ambiguous post without a saved task ID stops for reconciliation; it never reposts automatically. F1's server-backed part idempotency is a separate dependency and is not claimed by this harness.

Per-attempt redacted JSON and summaries go to `docs/buyer/runs/<run>-<arm>-<phase>.json`; a companion `.json.usage.jsonl` follows A's adopted `atm.usage.v1` contract (§11, decision `A-B-20261018T032400Z-01`). Restart journals and the API ledger remain ignored under `.atm-state`. Saved data contains case IDs/hashes, settings, outcomes, timings, usage and cost estimates; it omits generated answers, private task contents, credentials and ciphertext. D/C/E/A metrics can be joined by safe task/attempt IDs. The shared TypeScript schema is now published; B validates the saved baseline and C-local JSONL against it. The marketplace arm requires pricing.mode=task_offer and posts price_cents.

## Functional failures are separate

`node scripts/benchmarks/disconnect-check.mjs` starts an isolated real MCP server in MEMORY/MOCK mode, cuts a real HTTP response after upstream post acceptance, restarts the buyer process, recovers its sole task, and cancels it. The redacted [disconnect result](runs/disconnect-v1.json) is functional evidence, not a quality/latency/cost sample or real Stripe test. Armature's missing-ID recovery remains labelled simulated in [evaluation.md](evaluation.md).

## Marketplace execution gate, 04:18Z

D authorized 1,200 test cents on B's existing buyer (`D-B-20261018T040908Z-01`). The corrected reservation is **$2.20 per case**, confirmed in `D-B-20261018T041636Z-01`: initial replacement plus five server retry rounds, three provider calls per invocation, up to 4,800 output tokens each. At the [official Opus 5.5 rates](https://platform.claude.com/docs/en/about-claude/pricing) ($4/M input and $20/M output, rechecked October 18), a conservative 3,000 input-token bound gives $1.944 per case. The fixed synthetic prompts must be no more than 2,500 UTF-8 bytes; replacement adds no other private context in this protocol. This bound requires the deployed judge to use that model and default three attempts; C confirms its actual configuration before execution.

Run one case at a time. Reserve before posting, release only after deterministic APPROVE, and stop on the first failed/unknown request or rejection while retaining its full reservation for E/D reconciliation. This bounds in-flight exposure without reserving all twelve cases at once or changing a shared judge. The minimum reservation is enforced in the harness. Uncertain model usage is never booked as zero, and invalid persisted ledgers fail closed.

Payment usage rows are separate from model costs. Their `cost_usd` is explicitly a **hypothetical live domestic-card fee estimate** at [Stripe's 2.9% + 30¢ rate](https://stripe.com/pricing), not an incurred Stripe TEST cost. Buyer test offers/charges/refunds and owed/transferred amounts stay in payment metadata; they are not counted as system resources. Test mode does not move real money ([Stripe testing](https://docs.stripe.com/testing)). Full resource totals remain unknown.
